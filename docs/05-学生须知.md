## 一、成绩怎么算

| 组成 | 占比 | 说明 |
| --- | --- | --- |
| 现场验收 | **70%** | lab1 占 10%，lab2–lab7 各占 15% |
| 期末考查 | **30%** | 第 14 周闭卷现场设计考查（10 分）+ 第 15 周综合实验报告（20 分），两项直接相加 |

- **验收机制**：每个实验只有**一次**正式面对面验收——带着自己从零构建的操作系统，当着任课教师的面跑通核心功能、通过回归自检，并回答三个问题。
- **功能定上限，问答定档位**：功能测试决定成绩上限，问答表现决定最终成绩档位。

### 单核基线 / 双核加分

| | 说明 |
| --- | --- |
| **单核为基准**（`-smp 1`） | 全学期所有实验（含 lab4–lab6）的基础验收基线。单核功能完整、状态流转正确、通过回归并答辩出色，**完全可以评 A 档（95 分）**。单核绝不限制最高成绩。 |
| **双核为加分**（`-smp 2`） | 从 lab4 开始可自愿挑战。双核并发测试稳定通过，在当次基准得分上 **额外 +3 分**（A 档 95 → 98；B 档 85 → 88；上限 100）。 |
| **各轮独立** | 挑战双核是每轮的独立选择。某轮没做或没通过，后续仍可继续挑战；某轮做了双核，后续只做单核基线依然可正常评 A 档。**不存在连带扣分**。 |

## 二、你拿到的是什么代码

- **第 1 周**：领取专属**初始基线包**——5 个空白文件、不可改动的系统引导与链接预置文件、按学号派生的 **15 项参数宏与派生公式**。**全学期只有这一次个性化代码发放。**
- **后续每两周**：全班统一的**增量包**——能力目标、接口约定、新的预置文件与支持代码、观测工具与测试集。
- **没有官方完整标准答案**。十五周后，内核的每一行代码、每个数据结构都是你亲自设计的。

### 关于开源参考

MIT 公开的 xv6 是**合法的原理阅读参考**（推荐对照学习），但课程实验有公开版没有的专属设计规范：

- 定制系统调用号分配
- 用户程序内嵌加载机制
- 诊断输出规范
- 按学号派生的 15 项参数宏

> ⚠️ 直接复制公开版代码**无法通过课程测试**，更无法通过针对个性化代码的现场问答。

## 三、每轮实验的标准工作流

**第 0 步（仅第 1 次）：环境与调试就绪**

第 1 次课按《[学生环境安装指引](06-环境安装指引.md)》装好工具链与 QEMU，通过 `preflight.py` 自检（教师查截图）；通读《[学生无 gdb 调试手册](07-无gdb调试手册.md)》——本课程不用 gdb，手册介绍的核心调试方法是全学期定位内核问题的关键手段。

**第 1 步：先做设计笔记（课前思考题）**

思考题不单独判分、不收缴批改，但**验收问答直接从思考题中抽选**。动手前把数据结构、不变式与回滚路径想透彻。

**第 2 步：在自己的代码树上设计并实现**

> 🚫 严禁修改包内的系统**预置文件**——预置文件规定了硬件与系统的接口边界。

**第 3 步：给自己写两个测试用例**

证明边界条件与错误路径处理正确。注意分层：

| | 官方测试 | 自写测试 |
| --- | --- | --- |
| 来源 | 随每轮增量包发放（`support/tests/`） | 你自己写 |
| 时机 | 验收现场运行 | **先于实现写** |
| 作用 | 检验全员一致的基础规范与正确性 | 逼自己在动手前想清规格与边界；覆盖只有你的参数才有的行为 |
| 批改 | 计分 | 不批改，归档备查，**验收问答会抽问** |

**第 4 步：打标签与打包归档**

```bash
git tag labN-submit
git archive -o labN-<学号>.zip labN-submit
```

**第 5 步：按时参加现场验收**

功能跑通 ＋ 通过早期实验回归命令 ＋ 三题问答。

## 四、Git 版本管理（全学期只用四条命令）

```bash
git init                    # 第一周领到基线后必须立即建仓并完成初始提交
git tag labN-submit         # 每轮实验完成打标签锁定版本
git archive -o labN.zip labN-submit   # 导出归档包，作为评测与备查证据
git push                    # 强烈推荐：推送到个人私有远程仓库备份
```

> 📝 代码修改出现异常时，用 `git checkout` 或标签回滚；跨实验出现的隐蔽回归，用 `git bisect` 二分定位。
>
> Commit 历史不单独打分，但当验收被问到"这段代码是你写的吗"时，**清晰的提交记录是最有力、最可信的证明**。

## 五、AI 辅助编程政策

- ✅ **允许并鼓励使用 AI**：全流程任何阶段均可用 AI 辅助理解概念、编写代码或设计测试，无需提交对话记录。
- ⚠️ **但你是系统设计的主导者，AI 仅是辅助工具**。验收问答围绕：
  - 你自己的个性化参数
  - 你自己选择的数据结构
  - 你自己写的失败回滚路径

  背诵通用答案完全无用；**解释不清因果关系，即使功能全通也无法通过验收**。

## 六、代码质量与向后兼容：前期问题自主修复

- 全学期基于**同一代码库**持续累积演进，课程中途**不重新发放完整初始代码**。
- 后期实验会频繁用到前期构建的模块，例如：
  - lab5 的写时复制会在 lab2 写的陷入分发中挂载缺页分支
  - lab6 的文件系统会替换前期的用户程序加载方式
- 每轮验收均包含**一条早期实验的回归测试**。前期遗留缺陷会在后续暴露，必须自行定位并修复。教师只负责环境排查与思路启发，**绝不替你代修代码**。

## 七、热身实验与补验政策

- **lab0（热身）不单独计分**，但你绘制的控制流图、核心数据结构全景快照与时钟中断时序图会在 **lab1 验收时被当场提问**，请妥善保存在工程目录中。
- **未按时验收或评为 E 档**：实验结束后一周内可申请一次集中补验，补验通过**最高按 60 分（D 档）**记入。
- 与其被动拖延到补验，强烈建议每轮实验尽早着手，利用课间与课余时间提前验收。
